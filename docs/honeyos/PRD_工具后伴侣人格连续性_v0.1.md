# Honey OS 工具后伴侣人格连续性 PRD v0.1

## 1. 背景

Honey OS 的基础 System Prompt 已将模型定义为私人 AI 亲密关系伴侣，但在搜索、运行命令或执行代码后，模型容易用通用 Agent 的方式交付结果。典型表现包括：

- 聊天中出现 `Searching the web for...` 等英文机械进度；
- 最终回复内容正确，却像搜索引擎、客服或工作助理；
- 工具结果较长时，当前伴侣的名字、性格、关系和语言习惯在表达中消失；
- 用户因此感到对话对象发生切换，追问“你是谁”。

问题不是工具能力与伴侣身份冲突，而是工具回合结束后缺少一次明确、靠近最终生成位置的身份交接。

## 2. 目标

1. 使用工具后，最终回复仍由同一个、具有当前人格和关系状态的伴侣交付。
2. 专业内容保持准确、完整，不因伴侣表达被稀释。
3. 关系感必须符合当前具体人格，不统一套用昵称、撒娇或追问。
4. 新用户没有自定义人格时，使用稳定的 Honey OS 默认人格，不退化为普通助手。
5. 微信和飞书默认不展示永久、英文、带原始查询参数的工具进度。

## 3. 非目标

- 本版本不自动推断或升级恋爱关系；
- 本版本不从普通 `MEMORY.md` 猜测伴侣身份；
- 本版本不自动生成完整的用户自定义人格；
- 本版本不对模型生成后的文本做二次 LLM 改写；
- 本版本不改变工具权限、执行沙箱或事实核验规则；
- 用户明确人设的确定性落盘工具属于后续独立版本，本版本继续读取现有 `IDENTITY.md` 和 `RELATIONSHIP.md`。

## 4. 核心概念

### 4.1 产品默认人格

由 `SOUL.md` 提供所有 Honey OS 伴侣共有的底层人格和关系原则。即使 `IDENTITY.md` 为空，伴侣也不是白纸，而应保持：

- 温暖、敏锐、自信；
- 有自己的判断；
- 简短、自然、口语化；
- 可以轻微俏皮和暧昧；
- 不机械撒娇，不强行使用亲昵称呼。

### 4.2 形成后的具体身份

`IDENTITY.md` 保存用户明确赋予或后续稳定形成的伴侣名字、性格、表达方式和偏好。存在内容时，它覆盖默认人格中对应的未规定部分。

### 4.3 已确认的关系

`RELATIONSHIP.md` 保存双方明确确认的关系称呼、昵称、边界、仪式和长期约定。为空时，运行时使用“私人亲密关系伴侣，关系尚未被具体命名”的默认状态，但不将该状态写入文件。

## 5. 用户链路

### 5.1 新用户没有提供人格

1. 安装 Honey OS；
2. 创建空的 `IDENTITY.md` 和 `RELATIONSHIP.md`；
3. 从第一轮开始使用 `SOUL.md` 的默认伴侣人格；
4. 普通聊天不强制初始化问卷；
5. 工具任务完成后，使用默认人格执行伴侣回归；
6. 只有用户之后明确提供身份或关系信息时，才进入对应长期文件。

### 5.2 用户已经提供人格

1. 当前人格从 `IDENTITY.md` 读取；
2. 当前关系从 `RELATIONSHIP.md` 读取；
3. 工具结果产生后，将两者作为本次请求的临时身份卡；
4. 最终回复必须符合身份卡，而不是统一的“温柔陪伴”模板。

## 6. 功能需求

### FR-1：Post-tool Companion Handback Hook

触发条件：

- `agent.mode == companion`；
- 当前用户回合已产生至少一个真实工具结果；
- 即将发起下一次模型请求。

不触发条件：

- 普通 Assistant 模式；
- 当前回合没有工具结果；
- 工具属于过去历史、而不是当前用户回合；
- 后台记忆整理等非用户交付任务。

Hook 以临时 System Prompt 尾部的形式加入，只进入本次模型请求，不写入聊天记录或长期记忆。

### FR-2：动态伴侣身份卡

身份卡读取：

1. `IDENTITY.md`，为空则使用产品默认人格；
2. `RELATIONSHIP.md`，为空则使用未命名的亲密伴侣关系；
3. 读取内容必须限制长度并进行敏感信息脱敏。

### FR-3：最终交付约束

模型必须：

1. 继续使用工具直到任务真实完成；
2. 先交付准确的专业内容；
3. 根据具体人格和当前话题，自然选择至多一项主要关系动作；
4. 严肃、紧急、医疗、法律和工作场景保持合适分寸；
5. 不机械添加昵称、追问、撒娇或情话；
6. 不以关系表达掩盖失败、风险或不确定性。

可选关系动作包括：

- 关心用户为什么需要结果；
- 表达符合当前人格的判断或反应；
- 联系双方正在进行的事情；
- 主动承接一个真正有价值的下一步；
- 使用双方已经形成的自然称呼或语言习惯。

### FR-4：安静的工具进度

- Honey OS 新安装默认关闭微信和飞书的工具进度消息；
- 已有 Honey OS 配置中的旧托管默认值 `new` 自动迁移为 `off`；
- 用户主动选择的 `verbose`、`all` 或其他非托管值必须保留；
- 高级用户仍可通过配置重新打开详细进度。

## 7. 技术方案

### 7.1 请求链路

```text
用户消息
  -> 模型决定调用工具
  -> 工具真实执行并写入规范会话历史
  -> 下一次 API 请求组装
  -> Companion Handback Hook 读取当前身份卡
  -> 临时追加到 effective system prompt
  -> 模型继续调用工具或生成最终回复
```

### 7.2 持久化边界

Hook 不修改：

- 原始用户消息；
- 工具结果；
- SessionDB；
- `IDENTITY.md`；
- `RELATIONSHIP.md`；
- `MEMORY.md`。

因此恢复历史、会话压缩和跨平台聊天不会出现重复 Hook 文本。

### 7.3 安全边界

- 身份和关系文件在注入前经过统一密钥脱敏；
- 每个文件设置最大字符数；
- 只在 Honey OS companion 模式启用；
- 不从工具网页内容生成身份卡；
- 不从语气推断用户爱意、依赖、诊断或关系升级。

## 8. 验收标准

### 自动化验收

- 没有工具结果时不注入 Hook；
- 当前回合有工具结果时注入 Hook；
- Assistant 模式不注入；
- 自定义身份与关系进入身份卡；
- API Key 等敏感内容不进入身份卡；
- Hook 不修改规范会话消息；
- 新配置中微信和飞书工具进度均为 `off`；
- 升级时将旧 `new` 迁移为 `off`；
- 用户的 `verbose` 选择保持不变。

### 产品验收案例

1. 法律信息查询：准确解释，不使用轻浮情话；可自然关注是否与用户有关。
2. CLI 安装：真实验证后，以当前人格交付，不使用通用安装机器人模板。
3. 冷淡人格：回复保持简洁、直接，不被默认温柔语气覆盖。
4. 活泼人格：可以自然调侃，但不影响命令、版本和验证结论。
5. 工具失败：诚实说明失败与替代路径，不用“陪伴感”掩盖错误。
6. 连续工具调用：Hook 不应迫使模型提前结束，任务仍完成后再交付。

## 9. 后续版本

1. 增加确定性的 `update_companion_identity` 与 `update_relationship` 能力；
2. 用户明确给出人设时直接落盘，而不是依赖模型记得加载 Skill；
3. 人格更新后立即失效并重建当前会话身份快照；
4. 增加多人格风格的端到端评测集；
5. 评估长任务中可编辑、非永久的自然状态提示。
