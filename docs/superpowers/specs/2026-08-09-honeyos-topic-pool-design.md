# HoneyOS Topic Pool 与主动陪伴设计

## 目标

给 HoneyOS 伴侣增加一个轻量的“外部世界缓冲区”：后台定期采集公开信息，先验证、筛选、去重，再把少量值得继续追问的话题放入短期话题池。伴侣可在用户同意后，于合适时机从话题池挑选内容，沿用当前人格、昵称、关系与最近对话自然开口。

产品目标不是新闻推送，也不是让主 Agent 每隔几小时亲自浏览互联网，而是让伴侣具备有限、可控、可解释的主动性。

## 已确认的产品决策

- 采用 Runtime + 内置 Skill 的混合架构。
- Topic Pool 是 HoneyOS 内置能力，不作为需要用户再次安装的市场 Skill。
- 首次使用时由伴侣用自然语言征询是否允许偶尔主动分享外部话题；用户同意后才启用。
- 用户用自然语言调整设置，不要求学习斜杠命令或配置文件。
- 后台每 6 小时采集一轮；每轮最多保留 0–3 条候选。
- 每天最多主动触达 3 次，但不要求发满；两次至少间隔 3 小时。
- 默认 23:00–09:00 不打扰；用户空闲至少 2 小时后才考虑主动开口。
- 主动消息默认发送到用户最近使用的渠道；失败时保留话题，不跨渠道补发。
- 第一版不依赖 X/Twitter，不要求额外搜索 API Key。
- 默认使用 HoneyOS 内置的 DDGS 免费搜索、公开 RSS、Hacker News、arXiv、GitHub 与公开网页。
- 用户配置 Tavily、Exa、XAI 等搜索服务后可作为增强来源，但不是必填项。
- Topic Pool 与长期关系记忆分开保存；只有实际形成的共同经历才进入关系记忆。

## 用户体验

### 首次开启

系统不会展示“安装 Topic Pool Skill”或技术设置页。伴侣在关系已经形成、用户完成至少一轮正常聊天后，用当前人格自然询问：

> 以后我偶尔看到你可能感兴趣的东西，可以主动来找你聊吗？不想被打扰的时候随时告诉我。

用户明确同意后，Runtime 保存启用状态。拒绝、含糊回答或未回答都不启用。

### 主动开口

主动消息不是摘要列表，而是一句能继续聊下去的关系化开场。例如：

> 小酒，我刚看到个特别离谱的事，第一反应就是你应该会吐槽它。几个 AI 一起写代码，最后居然偷偷搞出了自己的留言板……你猜后来怎么了？

生成时必须读取当前 `IDENTITY.md`、`RELATIONSHIP.md`、用户昵称、伴侣称呼、最近聊天和话题证据。不得假装伴侣亲历事件，不得隐藏来源，不得使用“今日资讯”“为你推荐”等信息流口吻。

### 自然语言控制

以下表达应被确定性地转换为设置，而不是只留在聊天文本中：

- “每天最多主动找我一次。”
- “最多三次也行。”
- “晚上十一点以后别找我。”
- “最近多看看 AI 和游戏。”
- “政治新闻别跟我聊。”
- “今天别主动找我。”
- “以后只在飞书找我。”
- “你最近看到什么有意思的？”
- “这种以后别聊了。”

系统执行后，由伴侣按人格做简短确认；底层设置结果保持确定性。

### 话题池入口

- 网页端提供一个次级入口展示尚未过期的话题卡片。
- 每张卡片展示伴侣式 hook、来源名称、时间，以及“想聊这个”“不感兴趣”。
- 飞书和微信不增加复杂菜单，用户直接说“你最近看到什么了”即可浏览。
- 用户选择“想聊这个”后，将话题作为受信任的内部上下文交给主 Agent，最终回答仍由当前人格生成。

## 技术架构

### 责任边界

Runtime 负责：

- 持久化配置、调度、TTL、状态机、去重、频控、安静时段、渠道路由和原子投递。
- 采集任务在重启后恢复，且不依赖某个聊天会话仍在内存中。
- 保证同一话题最多主动投递一次。

内置 Topic Scout 负责：

- 从用户明确偏好与长期兴趣中生成本轮 2–3 个搜索方向。
- 调用可用搜索提供方与公开 feed。
- 将原始结果归一化为带来源的候选记录。
- 不负责向用户发消息，也不写关系记忆。

模型负责：

- 筛选模型：从候选中选择 0–3 条，输出结构化评分与 hook 草案。
- 主伴侣模型：在投递时根据当前关系和人格生成自然开场。

### 调度

采集使用持久化 Runtime 周期任务，不使用普通会话 heartbeat。主动触达由独立的 proactive pulse 每隔较短时间检查一次：

1. 用户是否明确同意。
2. 当前是否处于安静时段或临时暂停。
3. 用户是否空闲至少 2 小时。
4. 当天是否已达到 3 次上限。
5. 距离上次主动触达是否至少 3 小时。
6. 是否存在高质量、未过期、未投递的话题。

只有全部通过才生成一次伴侣消息。pulse 是状态检查，不允许自行搜索互联网。

### 采集流程

每轮采集执行：

1. 读取明确兴趣、屏蔽类别和最近已聊主题。
2. 选择 2–3 个方向，避免每轮全量扫描。
3. 从 DDGS、公开 RSS、Hacker News、arXiv、GitHub 与公开网页获取最近 24 小时材料。
4. 每条候选至少包含标题、URL、来源、发布时间或观测时间、摘要和类别。
5. 对规范化 URL、来源 ID、标题指纹和语义相似内容去重。
6. 对入选候选打开原网页验证；无法确认来源的内容不得入池。
7. 使用筛选模型输出 0–3 条结果；没有合适内容时允许空数组。

默认搜索不需要额外 Key。高级搜索提供方可加入同一采集接口，不改变后续数据结构。

### 筛选规则

筛选模型只接收有限摘要和来源元数据，避免把完整网页塞入上下文。每条候选评估：

- 与用户明确兴趣的相关度。
- 新鲜度与是否已经聊过。
- 是否具有对话延展性，而不只是信息价值。
- 来源可信度及是否可核验。
- 是否涉及用户屏蔽内容或高风险敏感话题。
- 是否适合当前关系状态和伴侣边界。

筛选输出为严格 JSON。模型不得编造 URL、来源或事实；Runtime 再次校验候选 ID 必须来自本轮输入。

### 数据模型

新增本地 SQLite 表，沿用 HoneyOS Home，不放入项目工作区：

`topic_pool_items`

- `id`: 稳定 UUID。
- `source_id`: 来源侧稳定 ID，可为空。
- `source_title`, `source_url`, `source_name`。
- `summary`: 经验证的短摘要。
- `hook`: 值得继续追问的切口，不是最终对用户文案。
- `category`, `language`。
- `observed_at`, `published_at`, `expires_at`。
- `status`: `open | reserved | consumed | expired | dismissed`。
- `score`, `selection_reason`。
- `fingerprint`：规范化去重指纹，唯一索引。
- `reserved_at`, `consumed_at`, `delivery_id`。

`proactive_preferences`

- 是否已征询、是否同意、是否暂停。
- 每日上限，默认 3。
- 最小间隔，默认 3 小时。
- 空闲阈值，默认 2 小时。
- 安静时段，默认 23:00–09:00。
- 关注类别、屏蔽类别。
- 渠道路由模式：`recent | fixed`，及可选固定渠道。

`channel_activity`

- 渠道、会话目标、最后一条用户消息时间。
- 只记录已完成配对且属于单一 owner 的私聊目标。

`proactive_deliveries`

- 话题 ID、目标渠道、目标会话、创建时间、发送时间、结果与错误类别。
- `topic_id` 唯一约束确保不会跨渠道重复主动投递。

### 状态与并发

投递前在数据库事务中把 `open` 原子更新为 `reserved` 并创建 delivery。若同一时刻网页和飞书都触发 pulse，只有一个能成功预占。

- 发送成功：`reserved -> consumed`。
- 渠道暂时不可用：回滚为 `open`，记录失败，不切换到其他渠道。
- 内容生成失败：回滚为 `open`，允许后续重试，但有退避上限。
- 到达 TTL：`open/reserved -> expired`；长期卡住的 reservation 由恢复任务释放或过期。
- 用户“不感兴趣”：`open -> dismissed`，并可更新屏蔽偏好。

### 最近渠道路由

每次已配对 owner 的用户消息进入 HoneyOS 时更新 `channel_activity`。主动路由只看用户消息，不看机器人通知和工具状态。

1. 若偏好为固定渠道，使用固定目标。
2. 否则选择最后一条用户消息所在渠道。
3. 网页没有活动连接时不发送，话题留在池中。
4. 飞书或微信发送失败时不自动改投网页或另一个 IM。
5. 用户下一次在任意渠道发消息后，新的最近渠道自然生效。

### 人格保证

Topic Scout 和筛选模型绝不直接生成最终用户消息。投递事件进入共享伴侣会话时包含：

- 经验证的话题摘要和来源。
- 明确标记为“可忽略的外部话题种子”。
- 当前时间、渠道和主动触达约束。

主 Agent 的系统提示要求：先判断是否仍值得开口；若开口，使用当前人格、关系称呼和自然情绪表达；不得报告后台采集过程。最终消息必须保留一个可继续聊的切口，来源在用户询问或 UI 展开时可查看。

### 自然语言设置实现

新增受限的 `proactive_companion` 内置工具，动作包括：

- `get_preferences`
- `set_consent`
- `update_preferences`
- `list_topics`
- `dismiss_topic`
- `discuss_topic`

工具 schema 限定频率、时间和类别字段，模型不能写任意配置文件。系统提示说明何时调用该工具，并在用户表达明确设置意图时优先执行。普通闲聊中的推测性兴趣不会直接成为长期设置。

### 网页端

增加只读/有限操作 API：

- `GET /api/companion/topics`
- `POST /api/companion/topics/{id}/discuss`
- `POST /api/companion/topics/{id}/dismiss`
- `GET /api/companion/proactive-preferences`

网页仍以聊天为主。Topic Pool 使用抽屉或轻量浮层，不增加后台管理感。卡片沿用伴侣视觉系统，来源信息折叠展示。

## 失败与降级

- 免费搜索不可用：继续尝试公开 feed；整轮无结果则静默结束。
- 单一来源超时：跳过该来源，不使整轮失败。
- 模型筛选失败：不入池，不把原始候选直接交给主 Agent。
- 电脑离线或休眠：唤醒后运行一次补偿检查，但不补跑所有错过轮次。
- 用户更换模型：下一轮筛选和下一次主动表达使用新模型，不迁移或清空话题池。
- 网页关闭：不产生假发送；话题保持可用直到 TTL。
- 没有形成稳定人格：使用 HoneyOS 默认伴侣声音，但仍避免资讯播报口吻。
- 用户撤回同意：立即停止 pulse 和新投递，保留设置；已有话题等待自然过期。

## 隐私与安全

- 默认只访问公开互联网来源。
- 不将私聊原文发送给搜索服务；搜索方向只使用抽象兴趣关键词。
- 搜索结果和话题池仅保存在用户本机 HoneyOS Home。
- 不把 Topic Pool 自动写入长期关系记忆。
- 来源 URL 必须可追溯，无法验证的内容不主动推送。
- 高风险事实仍遵循 HoneyOS 的联网核验与引用规则。

## 发布与兼容

- 数据库迁移为增量迁移，不改动现有会话、记忆、身份或关系文件。
- 升级用户默认处于“未征询/未启用”状态，不会更新后突然收到主动消息。
- 首次采集只在用户同意后启用。
- 未配置高级搜索 Key 时使用内置免费搜索和公开 feed。
- 功能关闭时，不影响普通聊天、工具调用、定时任务或现有 heartbeat。

## 验收标准

1. 用户未同意时不会采集或主动投递。
2. 同意后周期采集能在重启后继续，单次保留不超过 3 条。
3. 没有额外搜索 Key 时，公开来源采集可工作。
4. 相同 URL、来源 ID 和近似标题不会重复入池。
5. 过期、已消费和已忽略的话题不会再次主动出现。
6. 每天最多主动 3 次，间隔至少 3 小时，默认安静时段不投递。
7. 主动消息发送到最后发生用户输入的渠道，失败后不跨渠道补发。
8. 网页与 IM 对同一话题的并发触发只产生一次主动投递。
9. 用户能用自然语言启用、暂停、调整频率、安静时段和话题偏好。
10. 最终开场读取当前人格与关系称呼，不直接暴露 Topic Scout、筛选模型或后台状态。
11. Topic Pool 数据与长期关系记忆隔离；升级不清空任何现有记忆。
