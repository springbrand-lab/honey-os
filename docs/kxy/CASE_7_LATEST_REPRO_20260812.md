## 390px 布局证据

使用同源 390×844 iframe 执行实际浏览器布局，连续两次得到相同结果：

```json
{
  "viewport": { "width": 390, "height": 844 },
  "document": { "clientWidth": 390, "scrollWidth": 448 },
  "canvas": { "left": 0, "right": 390, "width": 390 },
  "allButtonsInViewport": false,
  "horizontalOverflow": true
}
```

六个按钮中最右侧 P2 方向键边界为 `x=372..436`。Canvas 已正确适配 390px，因此溢出来自控制区固定宽度按钮，不是 Canvas。

## 玩法不可完成证据

生成代码同时满足以下条件：

1. 两辆坦克的 `y` 都是 `H - 100`。
2. 炮弹初始位置是 `t.y - 5`，即位于坦克上方。
3. 炮弹速度固定为 `vy: -8`，之后只继续向上。
4. 命中要求 `b.y > t.y && b.y < t.y + t.h`。

炮弹从一开始就小于对方 `t.y`，之后只会更小，因此命中条件不可达。该静态可达性断言连续运行两次均得到：

```text
tank_hit_reachable: False
```

## 最终判定

**Case 7 最新回归失败。** 自动运行和网址交付已改善，但“手机可玩”的核心承诺不成立：窄屏控制区被裁切，且对战逻辑无法产生命中和胜负。这两个都属于重大问题，不能按“最终可用”处理。

## 建议修复方向

1. Build 完成前必须跑真实移动视口断言：`scrollWidth <= clientWidth`，所有可交互按钮完整位于视口内。
2. 对固定按钮尺寸增加窄屏媒体查询，或改成基于容器宽度的 `clamp()` / CSS Grid 布局。
3. 增加最小玩法测试：开始游戏、双方各执行移动/开火，断言生命值能够变化且能进入结束状态。
4. 生成前先快速发出 Build 状态事件，不应等模型一次性生成 3,878 tokens 后才显示首个行动卡。
